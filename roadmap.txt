3. Üç Drill Pattern — AI'la Çalışırken Bağımlı 
Olmamanın Yolu / Three Drill Patterns — How to 
Use AI Without Depending on It 
Senin asıl zaafın 'klavyede boilerplate yazamamak' değil. Asıl zaaf: AI'ın yazdığını okuyup doğrulayamamak, 
planlayamamak, bozulduğunda tek başına düzeltememek. Bunları saatlerce AI-off egzersiziyle değil, her 
projeyle birlikte uyguladığın üç pattern ile çözüyoruz. 
Your real weakness isn't 'can't type boilerplate'. It's inability to read, verify, plan, and debug what AI writes. 
We solve this not with hours of AI-off drills, but with three patterns applied inside every project. 
Pattern 1 — Okuma Drilli / Reading Drill (günde 20–30 dk) 
 AI bir dosya yazdıktan sonra o dosyayı kapat, geri dön, her satırı yüksek sesle açıkla (kendine) 
 Açıklayamadığın satırda dur. ChatGPT'ye sorma — resmi dokümana git (örn. FastAPI docs, SQLAlchemy 
docs) 
 Dosyanın sonunda bir cümleyle özet yaz: 'Bu dosya ne yapıyor, hangi sorunu çözüyor?' 
 Hedef: Hafta sonunda repo'daki her dosyayı 60 saniyede özetleyebilmek 
Pattern 2 — Plan Drilli / Planning Drill (her yeni feature'dan önce 30 dk, kağıt kalem)  
 Endpoint'leri listele: method + path + input + output 
 Pydantic modellerini çiz: field'lar, validations, optional mı? 
 DB tablolarını çiz: primary key, foreign key, index'ler 
 Data flow'u 1 sayfa ok+kutu diagram olarak çiz: user → FastAPI → LLM → DB → user 
 Başarı / hata senaryolarını yaz: en az 3 'ne yanlış gider?' sorusu 
 Ancak o zaman AI'ya git. Böylece AI mimari karar vermek yerine senin kararlarını kodluyor 
Pattern 3 — Debug Drilli / Debug Drill (haftada 1–2 saat) 
 AI'a: 'Bu kodun bir yerini gizlice boz, bana nereyi bozduğunu söyleme' dedir 
 Servisi çalıştır, bug'ı tek başına bul — AI kapalı 
 Hata mesajı, log, stack trace okuma pratiği bu sayede gelişir 
 Bulduktan sonra AI'a 'seçtiğin bozma yöntemi production'da nasıl bulunabilirdi?' sor — monitoring + 
test yazma refleksi oluşur 
Ayda Bir — Fundamental Refresh (2 saat, AI-off) 
 Ay 1: Cosine similarity numpy'la sıfırdan  Ay 2: BM25 formülünü elle uygula, 50 dok üzerinde test et

Framework Politikası — Mantığı / Framework Policy — The Reasoning 
Video'daki kural 'LangChain kötü, SDK iyi' değil. Asıl ilke: 'Sıfırdan yazmak, battle-tested karmaşık tooling'i 
tekrar icat etmek anlamına geliyorsa, kütüphane kullan. Aksi halde, doğrudan SDK ile yaz.' 
The rule isn't 'LangChain bad, SDK good'. The actual principle: 'Reach for a library only when rolling your 
own means reinventing battle-tested complex tooling. Otherwise, write directly with the SDK.' 
Doğrudan SDK ile Yazılan Yerler / Where We Write Directly With The SDK  
 Basit chatbot — 50 satır, OpenAI SDK + Pydantic yeterli 
 RAG — embed + retrieve + prompt; bağımlılık eklemeye değmez 
 Tek-tool agent (search, lookup) — function calling SDK'da var, manual ReAct 100 satır 
 Multi-tool agent (4-5 tool) — yine SDK + manuel orchestration; LangChain'in agent loop'u senin 
kontrolünden çıkar 
 Sebep / Reason: bağımlılık çok değişiyor, doc okuma yükü, debug zorluğu — video'daki yorum birebir 
İSTİSNA: SQL Agent için LangChain — Niye? / EXCEPTION: LangChain for SQL Agent — 
Why? 
Bir SQL Agent'ı sıfırdan yazsan, tekrar uygulaman gereken battle-tested altı şey var. Hiçbiri 'kolay' değil ve 
hepsi production'da patlayan yerler: 
 Schema introspection — information_schema'dan tablolar/kolonlar/tipler çıkar, LLM'e sun 
 Dialect-aware SQL generation — PostgreSQL ILIKE, MySQL LIMIT, BigQuery partition farklı 
 Iterative correction loop — LLM yanlış kolon yazar, DB hata döner, hatayı LLM'e geri ver, düzeltsin, retry 
 Result handling — 200K satır döndüyse truncate + summarize + paginated drill-down 
 Safety katmanı — read-only user, query timeout, row limit, SQL injection defansı, schema-level access 
control 
 Few-shot example injection — domain query örneklerini schema'ya göre dinamik prompt'a koymak 
Bunlar LangChain SQLDatabaseToolkit + create_sql_agent içinde test edilmiş. Sıfırdan yazsan 2-3 hafta 
gider, üstelik production'da edge case'lerle karşılaştığında patlayan sen olursun. Video'daki adamın 'yüz binlerce satırlık veride harika bir araç' demesinin sebebi tam bu — büyük datasette iterative correction 
olmadan LLM'in tek seferde doğru SQL üretme şansı çok düşük.

 LlamaIndex — Ay 2'de 1 gün karşılaştırma için denemek serbest, ama production'da SDK + custom 
kullanıyoruz
